# The generated views and their one writer

A brain's views are generated from its data: the kanban and the roadmap (`notes/kanban_graph.md`,
`notes/roadmap_graph.md`), the plan and module maps (`notes/plan_graph.md`, `notes/modules_graph.md`), the decision
queue (`notes/decision_queue.md`), the audit (`notes/audit.md`), `FEATURES.md`, and the graph's derived nodes and
edges (`notes/graph/nodes/_generated_*.yaml`, `notes/graph/edges/_generated_*.yaml`). `brain views` and `brain check`
know one the way the merge driver does (`brain.mergedriver`): `GENERATED by `` ` in its first five lines, or a name
that starts with `_generated_`. The module is `brain.views`, the command `brain views` (`brain.commands.views`).

Every branch used to regenerate them and commit them, so every merge of the default branch into a branch met them,
and two PRs merged in a row left the default branch's views a merge behind. One writer instead: a branch need not
commit its views; they are regenerated once on the default branch after each merge.

## What `brain check` asks, by where the checkout stands

| Where | A stale view |
|---|---|
| the default branch (HEAD on origin/HEAD's target, else `main`, else `master`) | a warning naming `brain views --write`, as before; under `views.strict` (below) an error: `brain check` and `brain refresh` exit 1 |
| any other branch, or a detached HEAD | one `views:` line saying which, never a warning nor an error |
| not a git checkout (or one with no commit yet) | a warning, as before |

On the default branch, `brain check` measures the decision queue, the links graph, the plan and module maps, the
records' graph, `FEATURES.md`, the kanban and the roadmap (the last two in this Python's research-graph; its own check
still prints its advisory). It does not measure the audit (`brain audit --write` writes it) nor
`_generated_decisions.yaml`, whose missing stubs research_graph check fails on wherever it runs. The scout
(`brain audit --diff`) no longer asks a branch for a fresh `FEATURES.md` (its check `features.md` is `never` in the
scout): the full audit and the default branch's check do.

### `views.strict`: the owner's opt-in

```json
{"views": {"strict": true}}
```

`config.json` `views.strict` (a boolean, default false) is how an owner opts in to the one writer's rules: a stale
view on the default branch fails `brain check` and `brain refresh` (exit 1), and the writers of one committed view
refuse an engine other than the pin (below). Without it, or false, the default branch's stale views are warnings and
those writers write with any engine, as before the one writer: an engine upgrade never newly refuses what passed.
Before setting it, bring the default branch's views up to date (`brain check` in the main checkout names the stale
ones; `brain views --write --commit` from a worktree at its tip, then merge that commit). `brain views --write` holds
its own output to the strict rules whatever the key: the writer never commits a stale view.

## On a branch

`brain sync` (and `brain refresh`) still write the views in the working tree: the branch's own checks read the
derived nodes they hold. Committing them is allowed, as before, and nothing refuses it; the merge driver's view kind
then keeps one side and marks it for `brain refresh` (the fallback, [merge-driver.md](merge-driver.md)). To leave
them to the writer:

```bash
git add -A
brain views --unstage        # the staged views out of the index; the working tree keeps them
git commit -m "..."          # the commit leaves them as HEAD had them

brain views --reset          # before merging the default branch: every view back at HEAD
git merge origin/main        # a local change to a file main brings would stop the merge
brain refresh                # written again for this branch's checks
```

`brain views` lists the tracked views, where the checkout stands, those changed or staged here, and those the merge
driver kept from one side (`--json`: `place`, `branch`, `default`, `tracked`, `changed`, `staged`, `merge_marks`).

## After each merge: `brain views --write`

The one writer runs in a worktree at the default branch's tip, never in a main checkout (the services run from it,
and `brain audit --write` and `brain features render --write` refuse it already):

```bash
git -C <repo> fetch origin
git -C <repo> worktree add -b chore/views-<date> <path> origin/main
brain --root <path> views --write --commit   # brain sync's writes, the audit view, brain check; then a commit
# push the branch and merge it the project's way (a views-only PR), then remove the worktree
```

`--write` runs what `brain refresh` runs (sync, then check) for each store of the project at that root, then
`brain audit --write` when the root keeps `notes/audit.md` (`--no-audit`: not), clears the merge driver's marks once
it passes, and lists every file it changed: the views and what sync derives with them (the features' statuses from
merged PRs, a spec turned active, a default taken). `--commit` commits those files alone (`git commit --only`): a file
that was already changed before it ran stays out, and nothing is committed when the check failed. Its check holds the
views to the default branch's rules even on its `chore/views-<date>` branch: a view its sync left stale is an error
there, as it would be on the default branch once the commit is merged. It says so when HEAD is not the default
branch's tip (the views written are then that branch's), and `--commit` commits nothing when HEAD lacks that tip
(`origin/<default>`, fetched first unless `--offline`, else `<default>`; or no default branch is found): views of a
stale base would undo the later merges' views (`git merge --ff-only origin/<default>`, then again). A views PR that
a later merge overtakes before it lands is regenerated the same way: one run covers any number of merges.
`--offline` skips gh and the fetch; `--force` writes with an engine other than `config.json` `engine.pin`, which
otherwise refuses (below). `--commit`, `--no-audit`, `--offline` and `--force` go with `--write` (refused without it).

Who runs it is the project's choice: the coordinator's merge step after a batch of merges, the owner, or later the
merger of `brain ship` (a merge queue). Until it runs, the default branch's `brain check` warns of the stale views
(fails under `views.strict`), which is the signal.
A brain whose owner works on the default branch itself regenerates there with `brain sync` (or
`brain refresh --on-main`), as before.

## Written by the pinned engine only

A committed view written by another engine than the brain's pin would differ from the one the pinned engine writes
(COMPAT-1, N10 of the data compatibility norms). `brain views --write`, `brain sync`, `brain refresh` and
`brain render --write` refuse to write then, each with the way out (`brain.skew`), unless `--force`. Under
`views.strict`, so do `brain audit --write`, `brain coverage --write`, `brain features render --write`,
`brain decision view --write`, `brain modules --write` and `brain reference --write` (`brain.skew.refuse_view`); without
it they write with any engine, as before.

## The technical reference

`brain reference` (`brain.reference`, `wi-brain-technical-reference`) writes a project's technical reference into
`docs/reference/`: `README.md`, the index of the modules of the store's registry (`modules.yaml`, or the one `config.json` `modules.store` names, [modules.md](modules.md))
with their features, items and decisions, then the decisions no module holds (« unplaced », counted: a debt line);
and `modules/<id>.md` per module: what it does (its features, have first), the decisions in force on each of its
nodes, the rules its items deliver, its specs, its items done and open, and its open questions (the pending DDRs about
its nodes). A node's module is its `props.module`; a module page reads the features and done items too, which is why
they carry one ([modules.md](modules.md)).

The decisions in force: the unit is the answered DDR (its question, the chosen option, who answered and when), with the
ADR it went to; an ADR no DDR went to shows by its title; an ADR some DDR went to (a batch of answers) never by its
title alone. A unit is about the nodes its DDR links (`links.items`, `links.specs`) or its ADR decides
(`decided_by`). On one node the newest answer is in force and the earlier ones fold under it; an ADR a REVERSAL
supersedes (`supersedes`, or status `superseded`) is marked so. No inference beyond: the decision log stays the
history.

- `brain reference` exits 1 when `docs/reference/` is not the render (each file named); `--write` writes it and
  removes a generated page no longer rendered (a module gone from the registry). A page is generated when its third
  line (after its title) opens with `GENERATED by `brain reference``: a page there without it is the owner's, never
  overwritten nor removed (`--write` says so and exits 1). A module's page is named after its id with any character
  outside letters, digits, `.`, `-` and `_` made a dash. Under `views.strict` another engine than the pin writes nothing
  (`--force`).
- The opt-in is the project's own render in `docs/reference/` (its `README.md` generated, not a public one), which
  `brain reference --write` writes: from then on `brain sync` writes it again and `brain check` on the default branch
  warns of it when stale (an error under `views.strict`), from the project's first store. A brain without it, or with
  an empty folder or a public render there, gets nothing.
- `brain reference --public --repo R --out <checkout>/docs/reference --write`: the neutral reference of a public repo,
  by feature domain (`README.md`, `domains/<domain>.md`), drawn only from that repo's features (their `public_title`
  and `public_id`, the repo's own code, linked from the repo's root, and its own docs): no module, spec, ADR, DDR, item
  nor rule of the private brain. A line `brain check --public` would refuse is said, and then nothing is written (exit
  1): set the feature's `public_title` or `public_id`. The engine's own is `docs/reference/` in its repo.

The reference has no date and sorts what it lists: the same graph gives the same files.

## Generated READMEs

A repo that holds `readme.yaml` at its root opts in to a generated `README.md` (`brain docs`, `brain.readme`,
`wi-brain-readme-sync`): the engine's template (`templates/readme/README.md.tmpl`), the repo's `readme.yaml` (the text:
what it is, why, how to start, its notes, the commands it quotes) and the facts of their sources: the repo's features
(counts by status and domain, the top ones by value, a link to its `FEATURES.md`), each quoted command's usage from its
`--help` (the brain command's from the running engine's own parser, another program's by running it in the checkout,
at a fixed width of 120 columns), and, for a private repo, the active specs, the five newest active ADRs (by the date their id starts with) and the
pending milestones that its features and items (`props.repo`) link to. A clone of a public repo (`config.json`
`public.repos`) gets the neutral render: the features' `public_title`, no spec, ADR, milestone nor item.

- `brain docs render` prints it; `--write` writes `README.md` and the repo's `FEATURES.md`. A `README.md` that is not
  generated (no `GENERATED by `brain docs render`` line) is replaced only with `--force`, once. Under `views.strict`,
  another engine than the pin writes nothing (`--force`), as for the other views.
- `brain docs check` exits 1 when `readme.yaml` misses a required field or breaks its schema, a quoted command is gone
  (its `--help` does not run), or `README.md` is not the render: a hand edit, or a stale render (a feature, a command's
  help or a linked node changed).
- `brain check` runs the same check for every repo of the project that holds `readme.yaml` (once, from the project's
  first store): an invalid `readme.yaml` or a gone command is an error; a stale `README.md` is a stale view, a warning
  on the default branch (an error under `views.strict`). A project with no `readme.yaml` is not read at all.
- `--repo R` picks one repo of the project (every one with `readme.yaml` by default); `--dir PATH` reads and writes
  another checkout than the registered one: a worktree of `--repo`, else of the root's repo (another repo's worktree
  needs `--repo` too, or it gets the root repo's facts). A target with no `readme.yaml` is said not concerned, never
  counted as checked. A `README.md` that is not UTF-8 is read with its bad bytes replaced: simply not the render.
- `brain audit` reads `readme.yaml` from the committed tree of an opted-in repo (check `readme.yaml`) and runs its
  quoted commands' `--help` in the repo's checkout with the running engine (check `help.quoted`); a repo without it is
  listed as not measured (not opted in), which changes the not-measured lines of an existing `notes/audit.md` (and
  `help.quoted` now applies to every repo, not only those with commands) until its next `brain audit --write`.

The README has no date and sorts what it lists: the same sources give the same file. Its quoted commands' usage comes
from the running engine, so render it with the pinned engine.
