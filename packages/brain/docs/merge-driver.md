# Parallel sessions: the merge driver, collisions and briefs

Many sessions working on one brain at once meet in three places: the files every branch rewrites (the generated
views, the logs, the graph), the code two branches change, and the briefs a coordinator writes for each session.
Three zero-token commands take the mechanical part of each: `brain merge-driver` (the module brain.mergedriver),
`brain collisions` (brain.collisions) and `brain brief` (brain.brief).

## `brain merge-driver`: the shared files merge by themselves

A brain's branches all write the same few files: `brain refresh` regenerates the kanban, the roadmap, the decision
queue and the audit; `brain journal add` and `brain adr new` append to the journal and the decision log; `brain item`
appends to the graph's YAML. Each merge of the default branch into a branch used to conflict there, and a session
resolved it by hand: keep both sides, then regenerate. Git can do that alone through a merge driver.

GitHub never runs a custom driver. It does not need to: the merges that conflict are the local ones, of the default
branch into a branch, in each worktree; the PR GitHub merges is then clean.

### Setup

1. `.gitattributes` names the paths. `brain init` writes these lines, and an existing brain adds them:

   ```
   notes/journal.md merge=brain
   notes/decisions.md merge=brain
   notes/kanban_graph.md merge=brain
   notes/roadmap_graph.md merge=brain
   notes/decision_queue.md merge=brain
   notes/audit.md merge=brain
   notes/modules_graph.md merge=brain
   notes/graph/nodes/*.yaml merge=brain
   notes/graph/edges/*.yaml merge=brain
   FEATURES.md merge=brain
   CHANGELOG.md merge=brain
   ```

2. The repo's git config defines the driver. The installer does it for the personal brain (its `merge` step); by
   hand, `brain merge-driver install --repo <brain>` prints the plan and `--apply` writes it (idempotent):

   ```
   merge.brain.name   = brain: views keep one side, logs union, YAML by id
   merge.brain.driver = "<the brain launcher>" merge-driver run %O %A %B %P %L
   ```

   The config is the repo's own (`git config --local`), shared by all its worktrees. Without it, git merges these
   paths as text, as before: the attributes alone change nothing.

### What it does, by kind of file

| Kind | Which files | The merge |
|---|---|---|
| view | a file whose first lines say ``GENERATED by` `` (the kanban, the roadmap, the decision queue, the audit, FEATURES.md), or named `_generated_*` | one side kept whole: the default branch's when one side is its version, else ours; the path is marked, and `brain refresh` regenerates it |
| log | `journal.md`, `decisions.md` | the union: what both sides appended, the new dated entries (`## YYYY-MM-DD`) in date order; an edit both sides made to the same old lines stays a conflict, and so does a new entry dated before the last entry both sides had |
| union | `edges/*.yaml` (one edge per line) | both sides' new lines, a line both added once, a line one side deleted gone; the same line replaced both ways stays a conflict; the result must load as YAML |
| changelog | `CHANGELOG.md` | the union in the Unreleased section only (an Unreleased section both sides opened at one place becomes one), where a `### Added` (or any subsection) both sides opened becomes one; a conflict anywhere else stays. A changelog without an Unreleased section whose entries are dated is a log, newest first when it is written so |
| yaml | any other `.yaml`/`.yml` that is a list of `id:` entries (`nodes/*.yaml`) | entry by entry: an entry changed on one side takes that side, new entries of both sides are kept where they were added (ours, then theirs), a deletion on one side applies, an entry changed on both sides is merged line by line, else key by key (its `props` one level down: a close on one side and a new prop on the other) and written as `brain item set` writes a node, else left as a conflict; the result must load and keep its ids unique, else the file is merged as text |
| text | anything else | git's own three-way merge (`git merge-file`) |

Whatever goes wrong falls back to `git merge-file`, so a file never loses its conflict markers. The driver writes the
result into `%A` and exits 0 when it resolved everything, 1 when markers remain, as git expects; its notes go to
stderr (`brain merge-driver: notes/kanban_graph.md (view): kept theirs (the default branch's); brain refresh
regenerates it`). The conflict style follows `merge.conflictStyle` (`diff3` and `zdiff3` show the base).

### After a merge

The views the driver kept from one side are listed in the worktree's git folder (`brain-refresh`):
`brain merge-driver status` shows them, `brain check` names them, and `brain refresh` clears the list once it passes.
So the routine after `git merge origin/main` is `brain refresh`, then commit.

### Checking it on a repo's history

`brain merge-driver replay` merges past merges again with `git merge-tree` (nothing is checked out, the working tree
is untouched), once as text and once with the driver, and counts the conflicted files of each:

```bash
brain merge-driver replay --repo <brain> --since 2026-11-01   # every merge reachable from HEAD since that day
brain merge-driver replay --repo <brain> <merge-sha>          # one merge commit
brain merge-driver replay --repo <brain> <head-a>..<head-b>   # two heads, as they are today (two PRs)
```

For each file the driver resolved, it also says whether its result is the one the merge commit recorded
(`--json`: `same` or `differs`; a view differs by design, the merge regenerated it).

## `brain collisions`: who can start now

Before a wave, the coordinator needs to know which items can run in parallel. `brain collisions` reads, for each repo
of the project (`--all`: every registered project):

- every linked worktree and every local branch the default branch does not hold, with the files it changes against
  the default branch (`git diff --name-only <default>...<branch>`) and, for a worktree, its uncommitted changes
  (untracked files included), and the desktop app's session of the worktree (live, archived, gone or unknown);
- the files the merge driver resolves (`git check-attr merge` says `brain`) are counted apart: two branches meet there
  at no cost;
- each startable item (todo, nothing it depends on open; P0 and P1, or `--frontier` for all), with its predicted
  surface: the CodeRefs of the features it `delivers`, the CodeRefs of its module's features (`props.module`,
  `props.modules_secondary`), and the file names its title and props name.

It prints the branches, the files two branches change, then the items in three groups: those that can start now, those
that wait (on a branch named after them, or on a branch that changes a file of their surface, with its session), and
those with no known surface. `--json` gives the same as data. A predictor plugs into
`brain.collisions.SURFACE_HOOKS` (`(node, store) -> [(repo, path)]`): wi-brain-touched-surface will add the files that
similar finished items touched.

## `brain brief`: a sub-session's brief from the graph

`brain brief <item> [--class trivial|standard|strategic] [--budget 400k] [--coordinator ID] [--notes DIR] [--write F]`
writes the brief a coordinator hands to a sub-session, so that it edits only what needs judgement:

- the item, its status and priority, every prop as recorded, its open questions;
- the task class with its model and effort, and the context budget: config.json `brief.classes` (default: trivial on
  `haiku` at `low` effort, 400k; standard on the coordinator's own model, 400k; strategic on `opus` at `high`, 800k);
- the cost estimate of `brain cost estimate`;
- the coordinator's app session id (`--coordinator`, else `$CLAUDE_CODE_HOST_SESSION_ID`, the session that runs the
  command) and the shared notes folder (`--notes`, else the desktop app's folder for that session when it exists);
- the item's subgraph (every edge in and out, the other node's type, status, title and anchor);
- its line of `brain collisions`;
- how to start: each repo's checkout and default branch (a session card cannot carry a source branch, so the brief
  says how to start from one);
- a « To decide » section the coordinator fills in;
- the definition of done and the never-list, copied from the owner's rules (config.json `rules`, then the project's
  `CLAUDE.md` and `AGENTS.md`): the section headed `brief.done` (default « Definition of done ») and the one headed
  `brief.never` (default « Never »), or without one the rules' sentences that start with « Never » and their « <owner>
  decides » lines. The engine writes none of them itself.

```json
"brief": {"classes": {"standard": {"model": "", "effort": "", "budget": "600k"}}, "never": "Never"}
```
